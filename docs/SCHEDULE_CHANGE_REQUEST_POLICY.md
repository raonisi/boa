# BOA CRM 일정 변경 요청 정책

이 문서는 일정 조회 권한, 직접 변경 권한, 일정 변경 요청 권한을 분리해 정의합니다. 모든 권한은 서버에서 검증하며 화면의 버튼 표시 여부만으로 허용하지 않습니다.

## 1. 기본 원칙

- 모든 `active` 역할은 조직 전체 활성 사용자의 일정과 현재 일정 조회 응답에 포함되는 업무정보를 조회할 수 있습니다.
- 일정 조회 권한은 일정 생성, 수정 또는 삭제 권한을 의미하지 않습니다.
- 일정 소유권의 기준은 `schedules.userId`입니다.
- `createdBy`는 실제 생성자를 기록하는 감사 정보이며 일정 소유권 판단에 사용하지 않습니다.
- `inactive`, `resigned` 사용자는 일정 조회, 직접 변경, 변경 요청, 승인 또는 반려를 수행할 수 없습니다.
- 현재 하나의 BOA CRM 운영 DB와 Railway 환경은 하나의 독립 조직만 서비스합니다. 멀티테넌시는 이 정책의 범위가 아닙니다.

## 2. 직접 일정 변경

| 역할 | 본인 일정 | 타인 일정 |
| --- | --- | --- |
| `branch_admin` | 생성, 수정, 삭제 가능 | 활성 사용자의 일정 생성 및 조직 내 일정 수정, 삭제 가능 |
| `sub_branch_admin` | 생성, 수정, 삭제 가능 | 직접 변경 불가 |
| `team_leader` | 생성, 수정, 삭제 가능 | 직접 변경 불가 |
| `member` | 생성, 수정, 삭제 가능 | 직접 변경 불가 |
| `inactive`, `resigned` | 불가 | 불가 |

일정 ID, 대상 사용자 ID 또는 수정 payload를 조작해도 위 기준을 우회할 수 없어야 합니다. 일반 사용자는 본인 일정의 `userId`를 타인으로 변경할 수 없습니다.

## 3. 일정 변경 요청 권한

일정 변경 요청은 타인 일정을 직접 변경하는 권한을 부여하지 않습니다. 요청은 `branch_admin`의 승인 전까지 일정 원본에 영향을 주지 않습니다.

### `sub_branch_admin`

다음 활성 산하 사용자에 대해 신규 일정 생성, 기존 일정 변경, 기존 일정 삭제 요청을 만들 수 있습니다.

- 직접 산하 `team_leader`
- 직접 산하 `member`
- 산하 `team_leader` 아래의 `member`

다른 부지점장 조직, 상급자, 동급자 또는 비활성 사용자에 대한 요청은 허용하지 않습니다.

### `team_leader`

직접 산하의 활성 `member`에 대해서만 신규 일정 생성, 기존 일정 변경, 기존 일정 삭제 요청을 만들 수 있습니다. 다른 팀, 상급자, 동급자 또는 비활성 사용자에 대한 요청은 허용하지 않습니다.

### `member`

타인 일정에 대한 변경 요청을 만들 수 없습니다. 본인 일정은 기존 직접 일정 API를 사용합니다.

### `branch_admin`

조직의 모든 일정 변경 요청을 조회하고 승인 또는 반려할 수 있습니다. 지점장 본인의 일정 관리는 기존 직접 일정 API를 사용합니다.

## 4. 요청 유형과 저장 기준

요청 유형은 `create`, `update`, `delete`입니다.

- `create`: 대상 사용자와 신규 일정 payload를 저장합니다.
- `update`: 일정 ID, 요청 시점의 기준 `updatedAt`, 변경 전 최소 snapshot, 실제로 변경되는 필드만 저장합니다.
- `delete`: 일정 ID, 요청 시점의 기준 `updatedAt`, 변경 전 최소 snapshot을 저장합니다.
- 사유는 필수이며 요청 및 검토 의견의 최대 길이를 서버 schema에서 제한합니다.
- 동일 일정에 대한 pending update/delete 중복은 서버와 DB 제약으로 방지합니다.
- 요청 저장 데이터는 승인과 감사에 필요한 일정 필드와 내부 식별자로 제한합니다.

변경 필드가 하나도 없는 update 요청은 `BAD_REQUEST`로 거부합니다.

## 5. 상태와 전이

| 상태 | 의미 |
| --- | --- |
| `pending` | 지점장 검토 대기 |
| `approved` | 승인과 일정 반영 완료 |
| `rejected` | 지점장이 반려 |
| `cancelled` | 요청자가 승인 전에 취소 |
| `conflict` | 원본 일정이 요청 이후 변경되어 자동 반영하지 않음 |
| `failed` | 승인 처리 중 검증 또는 반영 실패 |

허용 전이는 다음과 같습니다.

- 요청자: `pending`에서 `cancelled`
- `branch_admin`: `pending`에서 `approved`, `rejected`, `conflict`, `failed`
- 최종 상태의 요청을 다시 승인, 반려 또는 취소할 수 없습니다.

## 6. 요청 및 승인 시 재검증

서버는 요청 생성 시점과 승인 시점 모두에서 다음 조건을 재검증합니다.

1. 요청자와 대상 사용자가 `active` 상태인지 확인합니다.
2. 요청자의 현재 역할과 조직 계층이 대상 사용자에 대한 요청을 허용하는지 확인합니다.
3. update/delete 대상 일정의 소유자가 요청 대상 사용자와 일치하는지 확인합니다.
4. 고객 연결 일정은 요청자가 접근 가능한 고객인지 확인합니다.
5. 승인자는 `branch_admin`인지 확인합니다.
6. create 승인 시 대상 사용자가 여전히 활성 상태인지 확인합니다.
7. update/delete 승인 시 원본 일정의 `updatedAt`과 요청 시점 최소 snapshot이 모두 일치하는지 확인합니다.

조직 이동, 역할 변경, 퇴사, 고객 scope 변경이 발생해 승인 시점에 조건을 만족하지 않으면 요청을 일정에 반영하지 않습니다.

## 7. 원자성, 동시성, 충돌 처리

- 승인은 pending 상태를 조건부로 선점한 요청만 처리합니다.
- 동일 요청을 동시에 승인하는 경우 하나의 승인 처리만 성공해야 합니다.
- 승인, 반려, 요청자 취소가 동시에 발생해도 pending 상태를 먼저 선점한 하나의 전이만 성공해야 합니다.
- 일정 생성, 수정 또는 삭제와 요청 상태 변경은 하나의 DB transaction에서 처리합니다.
- transaction 실패 시 일정과 요청 상태가 부분 반영되어서는 안 됩니다.
- update/delete 요청 후 원본 일정의 `updatedAt` 또는 비교 대상 필드가 변경되면 `conflict`로 처리하고 자동 반영하지 않습니다.
- 같은 초 안에서 변경된 일정도 snapshot 비교와 전체 기준값 조건부 UPDATE로 감지합니다.
- 충돌 요청은 현재 일정과 변경 내용을 다시 확인해 새 요청으로 제출해야 합니다.

## 8. 승인 반영 기준

- create 승인: `schedules.userId`는 요청 대상 사용자, `createdBy`는 승인한 `branch_admin`으로 기록합니다. 요청자는 `schedule_change_requests.requesterId`로 추적합니다.
- update 승인: 요청에 저장된 변경 필드만 반영하며 요청에 없는 필드는 유지합니다.
- delete 승인: 기존 일정 삭제 정책에 맞춰 soft delete 또는 비활성 처리합니다.
- update로 일정 소유자를 바꾸는 기능은 제공하지 않습니다.
- 승인 후 알림 예약과 Google Calendar 동기화 같은 외부 side effect는 DB transaction 성공 이후 수행합니다.
- 요청 승인으로 생성하거나 수정한 일정의 개인 Google Calendar 대상은 실제 소유자인 `schedules.userId`로 제한합니다.
- 삭제 승인 후에는 기존 Google Calendar sync row를 기준으로 외부 이벤트 삭제를 시도합니다.

## 9. 알림, Push, 활동 로그

- 요청 생성, 승인, 반려, 충돌, 실패, 취소 이벤트는 필요한 대상에게 내부 알림을 생성할 수 있습니다.
- Push 제목, 본문, data payload와 활동 로그 metadata에는 고객명, 전화번호, 생년월일, 상담내용, 질병정보, 상품명, 보험료, token, credential 또는 secret을 포함하지 않습니다.
- 활동 로그에는 actor, 요청 ID, 요청 유형, 상태, 대상 사용자 ID, 일정 ID 등 최소 식별정보만 남깁니다.
- Google Calendar 동기화 실패는 DB 승인 결과를 되돌리지 않으며 별도 운영 실패로 기록하고 재처리할 수 있어야 합니다.

## 10. UI 정책

- `branch_admin`은 요청 목록, 상태별 요약, 상세 비교, 승인, 반려 기능을 사용할 수 있습니다.
- `sub_branch_admin`, `team_leader`는 허용된 산하 사용자 일정에서 생성·변경·삭제 요청을 만들고 본인 요청 상태를 확인할 수 있습니다.
- 요청자는 pending 상태의 본인 요청만 취소할 수 있습니다.
- `member`에게 타인 일정 요청 CTA를 제공하지 않습니다.
- 모바일에서도 승인과 반려 버튼의 오조작을 막고 처리 중 중복 클릭을 차단합니다.
- 화면 접근 제어와 무관하게 모든 요청·승인 권한은 서버가 최종 검증합니다.

## 11. 필수 회귀 기준

- 모든 active 역할의 조직 전체 일정 조회를 유지합니다.
- `branch_admin`의 직접 일정 관리 권한을 유지합니다.
- 일반 사용자의 본인 일정 직접 관리 권한을 유지합니다.
- 직접 일정 변경 권한과 일정 변경 요청 권한을 혼용하지 않습니다.
- inactive/resigned 접근 차단을 유지합니다.
- 일정 고객검색, 알림, Push, Google Calendar 연동의 기존 보안 정책을 유지합니다.
- 테스트 fixture에는 실제 운영 고객정보를 사용하지 않습니다.

## 12. 제외 범위

- 멀티테넌시와 `organizationId`, `branchId`, `tenantId` 추가
- 요청자의 직접 승인 또는 자동 승인
- 운영 DB를 사용한 테스트
- 고객정보를 포함하는 Push 또는 활동 로그
- 요청 승인 전 일정 원본의 선반영
